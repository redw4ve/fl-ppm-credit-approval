# Federated Learning for Predictive Process Monitoring in Credit Approval

Can several banks train a shared predictive process monitoring model on their own event logs without exchanging raw
data and what does that cost the individual bank? This repository is the implementation behind a TUM M.Sc. thesis
that answers those two questions using two public credit-approval event logs.

The empirical focus is non-IID heterogeneity, client fairness and the comparison of aggregation strategies. The model
is one multitask LSTM with three heads: The multiclass application outcome, the next activity and the remaining time
to the decision. Every stochastic step uses the fixed seed 42.

**Author:** Cornelius Weiss, TUM M.Sc. Wirtschaftsinformatik.
**Supervisors:** Michel Kunkler, TUM Chair I17 Rinderle-Ma. Angelika Schumann, zeb Consulting.

## What is and is not in this repository

Included: Every pipeline script and notebook, all seven workflow scripts, the full test suite, the approved schema
and mapping inputs and the pinned `requirements.txt`.

Not included: The raw event logs, the processed splits, the prefix tensor cache and the training outputs. All of them
are regenerated by the pipeline and the raw logs are fetched from their public source by
`_helpers/download_bpic_from_4tu.py`. The `.gitignore` keeps every generated artifact out of the repository.

## Final Pipeline Workflow

The repository-root `WORKFLOW_run_FULL_PIPELINE.sh` is the production orchestrator for the thesis hand-in run. 
A bare `bash WORKFLOW_run_FULL_PIPELINE.sh` reproduces the locked configuration. It starts from the existing processed 
splits by default and encoding is off by default, so it reuses the existing E_04 metadata and the warm prefix cache. 
Raw data download, preprocessing and encoding stay opt-in, because the frozen splits and encoded metadata have not 
changed since the last run and enabling them overwrites data or spends money in the API. The `--full` switch turns 
on the whole reproduction bundle at once and is what a fresh clone needs. The individual environment variables 
`RUN_DATA_DOWNLOAD=true`, `RUN_PREPROCESSING=true` and `RUN_ENCODING=true` remain available for a single stage.

The run writes one unified output root, `E_training/training_outputs`, with `baselines/`, `federated/` and 
`secure_aggregation/` subfolders, plus `differential_privacy/` only when DP is launched. E_07 reads this single root 
and joins baselines and federated (and DP when present) into one analysis, and it never discovers the 
secure-aggregation POC runs. DP is excluded from the bare run and launched separately with `RUN_FEDERATED_DP=true` 
into the same root.

The master calls only three training workflows and holds no training hyperparameters. The single source of truth for 
those lives in the workflows: The baseline workflow runs the joint baselines too, the federated workflow runs the joint 
federated runs too and defaults `STRATEGY=both` at `FEDPROX_MU=1e-4` and the DP workflow owns the DP defaults and 
epsilon grid.

Stage order: Optional download, optional preprocessing, optional encoding, E_05 baselines (including joint), 
E_06 federated (including joint), the optional E_06 DP epsilon sweep, the secure-aggregation POC, the E_07 analysis 
and the E_08 outcome robustness report.

Default production switches:

- `CLEAN_ENCODING=false` and `CLEAN_CACHE=false`: the generated E_04 metadata and the prefix tensor cache are
  deleted manually before the final run, so the master does not delete them.
  Encoding regenerates the metadata and training rebuilds the cache from scratch.
- `RUN_FEDERATED_DP=false`: the DP epsilon experiment is excluded from the bare run, so cloning the repository
  onto a laptop never blocks the matrix for days.
  Switch it on with `--dp` or `RUN_FEDERATED_DP=true` to sweep three BPIC 2017 splits over epsilon 1, 5, 10 and 50
  with FedProx at the fixed mu 1e–4 (12 runs).
  It needs CUDA and a DP request without CUDA aborts in the preflight.
  The DP workflow defaults to `STRATEGY=fedprox`, t_max 35, floor 1e-5 and patience 7.
  The DP workflow script itself is the launch procedure on a CUDA machine.
- `RESILIENT=true`: a single failed training run is logged to `FAILED_RUNS.log` under the output root and skipped,
  so the multi-day matrix continues.
  Encoding stays fail-fast, and E_07 reports any missing matrix entries.
- `RUN_TEST_SUITE=true`: the full test suite runs as the first stage of every invocation.
  It is self-contained and needs no data, a red test stops the run before any long stage starts and a green suite
  is the user-facing proof that the shipped code works.
- `RUN_FOCUSED_TESTS=false`: focused joint and reporting unit tests are opt-in.
- `RUN_LLM_EXPERIMENT=false` and `RUN_LLM_SCHEMA_EXPERIMENT=false`: the LLM side experiments are opt-in and only
  run inside the encoding stage.
  Running them needs an `OPENAI_API_KEY` for an account with active billing.
  A missing key never aborts the pipeline; it disables the two experiments, prints a banner and writes the marker
  file `E_prefix_encoding/mappings/llm_mapping/llm_analysis/LLM_SKIPPED_MISSING_OPENAI_API_KEY.txt`.
- `REPORTING_PROFILE=compact`: E_05 and E_06 write one consolidated run report plus plots, checkpoints, logs and
  prediction files.
- `RUN_TRAINING_ANALYSIS=true`: E_07 generates the Markdown, JSON and CSV analysis from the completed training
  outputs, then E_08 writes the outcome final-prefix robustness report besides it.
- `RESILIENT` also controls strictness.
  `--strict` (or `RESILIENT=false`) aborts on the first failed training run and passes `--strict` to E_07 and E_08,
  so any recorded warning fails the run.
Use `REPORTING_PROFILE=debug` only when the legacy standalone JSON fragments are needed beside the consolidated run report.

### What a bare run does and does not produce

A bare `bash WORKFLOW_run_FULL_PIPELINE.sh` runs the full test suite first, then the E_05 baselines, the E_06
federated matrix, the three-run secure-aggregation POC and the E_07 and E_08 analysis. It does not run the DP grid, 
the E_04 encoding regeneration, the LLM experiments, the decentralized metadata POC, preprocessing or the dataset 
summaries. Each omission is a documented default and the switches above enable the missing stages. A bare run therefore 
reproduces the training matrices from the existing metadata and does not reproduce the full thesis pipeline on its own.

Use `--full` for everything a bare run leaves out. It sets the download, preprocessing, encoding, cache-rebuild and
LLM stages in one switch, so a fresh clone needs no environment variables at all. It deliberately leaves the DP grid
off, because that needs CUDA and days of runtime, and `--full --dp` composes when both are wanted.

The clean thesis run must rebuild the prefix tensor cache, because the cache identity is changed by design and a
pre-existing cache must not survive into the clean run. It must also regenerate the E_04 metadata whenever that is
absent, for example, on a fresh clone or after the pre-run archive step. `--full` covers both.

## Reproducing the Run from a Fresh Clone

Build the environment first. Every reported number was produced with the pinned versions in `requirements.txt`.

```bash
python3.12 -m venv fl-ppm
./fl-ppm/bin/python -m pip install --upgrade pip
./fl-ppm/bin/python -m pip install -r requirements.txt
```

The pins in `requirements.txt` were resolved under Python 3.12, so the venv must use that interpreter.

> Run the test suite. It ships with the repository and must be green before the pipeline is trusted.

```bash
./fl-ppm/bin/python -m pytest tests/ -q
```

Export the OpenAI key first when the LLM side experiments should run. The key belongs to an account with active
billing, is read from the environment on every invocation and is never stored. Put the export into `~/.zshrc` to have
it in every shell.

```bash
export OPENAI_API_KEY="sk-your-key"
```

Reproduce the full thesis run from the raw logs. This downloads the BPIC logs, re-runs preprocessing, regenerates the
E_04 metadata, rebuilds the prefix tensor cache and runs every matrix, so it takes a few days.

```bash
bash WORKFLOW_run_FULL_PIPELINE.sh --full --strict
```

`--full` is the switch a fresh clone needs. It downloads the raw logs when they are missing, reruns preprocessing and
encoding, rebuilds the prefix tensor cache from scratch and runs both LLM side experiments when the key is set. The
download skips a log that already exists, so the switch is also safe on a warm checkout. Add `--dp` to include the DP 
grid, which needs CUDA and roughly 49 hours on top. Preview the plan without touching anything by adding `--dry-run`.

Reproduce only the training matrices from the existing processed splits and E_04 metadata.

```bash
bash WORKFLOW_run_FULL_PIPELINE.sh
```

Add the DP-SGD epsilon grid. It requires CUDA and aborts in the preflight otherwise.

```bash
bash WORKFLOW_run_FULL_PIPELINE.sh --dp
```

Preview the planned stages without executing anything.

```bash
bash WORKFLOW_run_FULL_PIPELINE.sh --dry-run
```

`bash WORKFLOW_run_FULL_PIPELINE.sh --help` lists every switch. Each one also exists as an environment variable.

## Repository Structure Decisions

Two structural properties of this repository are deliberate. Each is recorded here so a reader does not mistake
them for carelessness.

**The two dataset pipelines stay separate.** `A_02`, `A_03`, `B_02` and `B_03` are self-contained scripts rather than
one parameterized module. Roughly 780 lines are duplicated across the two dataset families. The datasets differ
in ways that reach into every stage. BPIC 2017 is not filtered by lifecycle transition while BPIC 2012 is filtered to
`COMPLETE` before the targets are built. The recognized outcome events differ, `O_Accepted`, `A_Denied` and
`A_Cancelled` against `A_APPROVED`, `A_DECLINED` and `A_CANCELLED`. They also sit at different levels of the process.
The partitioning features differ too, because BPIC 2017 carries `LoanGoal` and offer attributes while BPIC 2012 has
only `AMOUNT_REQ`, which is why BPIC 2012 has no strong split. Merging the two would push these differences into
branches and flags, so a reader auditing one dataset would have to reason about the other one at every step. Keeping
them separate means each dataset's preprocessing reads end to end on its own. That matters more here than avoiding
repetition, because these scripts define the data on which every reported number rests. The cost is the measured
duplication, about 77 percent of `B_02` and 74 percent of `B_03`, which is accepted and recorded rather than removed.

**Pipeline modules are loaded through `importlib`.** Pipeline modules are named by their stage, `04_1` through
`04_7`, so the filename carries the execution order and the repository reads in the order the pipeline runs. A Python
identifier cannot begin with a digit, so `import 04_5_encoding` is a syntax error. The modules are loaded through
`importlib.import_module` with the dotted path given as a string instead. The imports are still static. They resolve
once while the module is loading. The dependency graph is fixed and acyclic. There is no runtime plugin behavior. 
This is a naming tradeoff, taken because stage-ordered filenames are the primary navigation aid in a multi-stage pipeline.

## BPIC 2017 Core Pipeline: Preprocessing and Client Split

**Input:** 
- Event log `L`
- Number of clients `K` (3 or 5)
- Split strategy `s` (iid, weak, medium, strong)
- Split ratio `r = (0.6, 0.2, 0.2)`  

**Output:** 
- Per-client splits with train/validation/test
- Centralized splits -> per-config union of the bank splits
- Metadata and validation report

Model-facing vocabularies are built in `E_prefix_encoding`, not in Step 02.

| Step | Operation                                                                          |
|-----:|------------------------------------------------------------------------------------|
|    1 | Load `L` from XES, or read the cached Parquet file if available.                   |
|    2 | Derive target events: `NextActivity`, `RemainingTime` and `TimeDelta`.             |
|    3 | Derive case-outcome from the recognized outcome event.                             |
|    4 | Remove cases without an outcome event.                                             |
|    5 | Keep cancelled cases and encode their outcome as class 0.                          |
|    6 | Assign each remaining case to exactly one simulated bank using split strategy `s`. |
|    7 | For each bank `k ∈ {1, ..., K}`, sort cases by case start time.                    |
|    8 | Split each bank temporally into train, validation and test sets using `r`.         |
|    9 | Write the corresponding event rows to the bank-specific split files.               |
|   10 | Build centralized splits as the union of the bank train/validation/test splits.    |
|   11 | Persist split files, metadata and validation report.                               |


### BPIC 2017 Decisions

| Topic                 | Implemented decision                                     |
|-----------------------|----------------------------------------------------------|
| Raw log check         | Assert 1,202,267 events and 31,509 cases.                |
| Outcome labels        | `O_Accepted = 2`, `A_Denied = 1`, `A_Cancelled = 0`.     |
| Excluded activity     | `A_Pending` is not used because it follows `O_Accepted`. |
| Non-terminal activity | `A_Accepted` is not used as outcome.                     |
| Truncation            | Drop 98 cases without outcome event.                     |
| Cancelled cases       | Kept as outcome class 0.                                 |
| Zero-amount cases     | Kept and routed by split strategy.                       |

### BPIC 2017 Split Logic

Before any reassignment, the cases that would fulfill the criteria for assignment (by `LoanGoal` and `Outcome`), are 
shuffled and then reassigned one by one. So the assigment out of the pool is random but seeded with 42.

| Config          | Algorithm                                                                  | Zero-amount routing               | Enforcement          |
|-----------------|----------------------------------------------------------------------------|-----------------------------------|----------------------|
| `iid_3banks`    | seeded shuffle and round-robin                                             | included in shuffle               | none                 |
| `weak_3banks`   | weak amount-quintile soft mix                                              | equal A/B/C                       | none                 |
| `medium_3banks` | medium amount-quintile soft mix + LoanGoal moves + light rate enforcement  | A 50%, B 25%, C 25%               | A-B 5 pp, B-C 7 pp   |
| `strong_3banks` | medium amount-quintile soft mix + LoanGoal moves + strong rate enforcement | all A                             | A-B 10 pp, B-C 15 pp |
| `medium_5banks` | D/E specialist carve-out, then medium A/B/C logic                          | A 50%, B 25%, C 25% in A/B/C pool | A-B 5 pp, B-C 7 pp   |
| `strong_5banks` | D/E specialist carve-out, then strong A/B/C logic                          | all A in A/B/C pool               | A-B 10 pp, B-C 15 pp |


Amount-quintile weights for BPIC 2017: The log is split into five quintiles by `RequestedAmount`. Cases are then sampled
from those quintiles for the fraction of the weights below.

| Split        | Q1 low      | Q2          | Q3          | Q4          | Q5 high     |
|--------------|-------------|-------------|-------------|-------------|-------------|
| weak A/B/C   | .30/.30/.40 | .35/.30/.35 | .40/.35/.25 | .45/.40/.15 | .50/.40/.10 |
| medium A/B/C | .05/.30/.65 | .20/.30/.50 | .40/.40/.20 | .55/.35/.10 | .75/.20/.05 |

LoanGoal logic: The grouping is based on `01_approval_by_loangoal.png`, which reports approval rate and case count per 
`LoanGoal`. Clearly high approval goals are moved toward Bank A, while clearly low approval goals are moved toward Bank C.
`Home improvement` and `Existing loan takeover` are excluded from this grouping because they define specialist Banks D 
and E in the 5-bank setting. `Car` is also excluded because it is the majority class, has an approval rate close to average
and therefore does not provide a meaningful specialization.

| Bank | LoanGoal rule                                                                                                                                                                 |
|------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| A    | receives high-approval goals: `Remaining debt home`, `Boat`, `Caravan / Camper`, `Unknown`                                                                                    |
| C    | receives low-approval goals where size constraint allows it: `Tax payments`, `Not speficied`, `Other, see explanation`, `Extra spending limit`, `Motorcycle`, `Business goal` |
| D    | all `Home improvement` cases in 5-bank runs                                                                                                                                   |
| E    | all `Existing loan takeover` cases in 5-bank runs                                                                                                                             |

Generated BPIC 2017 outcomes: Spread and dropped cases

| Config          | Approval spread | Cases dropped |
|-----------------|----------------:|--------------:|
| `iid_3banks`    |         0.97 pp |             0 |
| `weak_3banks`   |         3.05 pp |             0 |
| `medium_3banks` |        12.00 pp |           495 |
| `strong_3banks` |        25.01 pp |         2,193 |
| `medium_5banks` |        14.21 pp |           390 |
| `strong_5banks` |        25.02 pp |           985 |

Approval-rate enforcement cap: The cap limits how many cases may be dropped from each affected bank during rate enforcement.
This prevents the medium and strong splits from reaching their target gaps by discarding too much data.

| Config                            | Cap per affected bank | Meaning                                                             |
|-----------------------------------|----------------------:|---------------------------------------------------------------------|
| `medium_3banks`                   |                    8% | At most 8% of Bank A and 8% of Bank C may be dropped.               |
| `medium_5banks`                   |                   10% | Higher cap because D/E specialist carve-out reduces the A/B/C pool. |
| `strong_3banks` / `strong_5banks` |                   25% | Highest cap for stronger approval-rate divergence and stress test   |

## E_05 Baseline Training Defaults

The multitask LSTM baseline workflow in `E_training/WORKFLOW_run_baseline_final.sh` was retuned after the first full
BPIC 2017 medium 3-banks centralized run.
The earlier defaults overfit at epoch 2 and pushed the outcome head into majority-class collapse under unweighted
cross-entropy.

Locked workflow defaults:

- `LEARNING_RATE = 2.5e-4` (halved from 5e–4 to push the best validation epoch from epoch 2 to roughly epoch 4)
- `WEIGHT_DECAY = 1e-4`
- `DROPOUT = 0.30`
- `EARLY_STOPPING_PATIENCE = 7`, uniform across the matrix
- `MAX_EPOCHS = 40` and the federated `MAX_ROUNDS = 40`, chosen so early stopping and not the budget terminates
  every run
- `LR_SCHEDULER = cosine` with a per-dataset-family period and floor: BPIC 2017 uses `LR_SCHEDULER_T_MAX = 15` and
  `LR_SCHEDULER_MIN_LR = 1e-6`, BPIC 2012 and joint use `LR_SCHEDULER_T_MAX = 35` and `LR_SCHEDULER_MIN_LR = 1e-5`
- `NEXT_ACTIVITY_HEAD_AGG = equal` is the locked federated head-aggregation default for joint runs in
  `WORKFLOW_run_federated_final.sh` and E_06; it is a strict no-op on single-dataset runs
- `HIDDEN_SIZE = 128`, `NUM_LAYERS = 2` (the larger 256 / 3 trunk evaluated in the third tuning pass did not lift
  any test metric and hurt next-activity macro F1, so the smaller trunk is locked)
- `OUTCOME_LABEL_SMOOTHING = 0.10` on the outcome cross-entropy head
- `OUTCOME_CLASS_WEIGHT_POWER = 0.5`: power 0 reproduces unweighted CE, power 1 keeps full inverse-frequency and
  intermediate values temper between the two
- `OUTCOME_HEAD_DROPOUT = 0.45` for the outcome head
- The E_05 module carries `OUTCOME_LABEL_SMOOTHING = 0.10` and `OUTCOME_HEAD_DROPOUT = 0.45` as its own defaults,
  so a bare module invocation resolves the same config as the workflow.
  A test compares every shared knob of the module against the workflow defaults.
- `OUTCOME_LR_SCALE = 0.3`, `NEXT_ACTIVITY_LR_SCALE = 1.0`, `REMAINING_TIME_LR_SCALE = 1.0`: per-head AdamW
  parameter groups, the outcome head trains at 30% of the trunk LR and the other two at the trunk LR.
  The sandbox-preferred `REMAINING_TIME_LR_SCALE = 1.5` is documented but not adopted.
- Loss contribution weights `OUTCOME_LOSS_WEIGHT = 1.0`, `NEXT_ACTIVITY_LOSS_WEIGHT = 0.5`,
  `REMAINING_TIME_LOSS_WEIGHT = 0.5` are locked; changing them alters task contribution and was not selected from
  the sandbox tests.
- `REMAINING_TIME_TRANSFORM = raw`, `REMAINING_TIME_SCALING = zscore` and `REMAINING_TIME_HUBER_BETA = 0.1` are the
  final training-side compatibility settings for the E_04 target representation.
- Historical note: `LEARNING_RATE_BPIC2017` and `LEARNING_RATE_BPIC2012` were evaluated as opt-in per-dataset
  learning-rate overrides, but the final E_05 scripts use one global `LEARNING_RATE`.
- Historical note: `OUTCOME_TEMPERATURE_SCALING` was evaluated as an optional supplementary calibration block, but
  the final E_05 scripts keep raw argmax as the official outcome metric and do not write a calibration artifact.
- Every compact run writes `E_05_run_report.json` or `E_06_run_report.json`, checkpoints, curves, prediction
  parquet files and CSV logs.
  `REPORTING_PROFILE=debug` additionally writes the legacy standalone JSON fragments for manual debugging.
- Prefix tensor cache moved from `OUTPUT_ROOT/prefix_tensor_cache` to `E_training/prefix_tensor_cache` so cached
  tensors survive deletion of the output folder.
- Checkpoint selection uses the best `val_loss_total` epoch only; the per-head best-epoch records and the
  remaining-time train-median baseline are diagnostic and do not influence the saved checkpoint.
